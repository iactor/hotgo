# 多门店直营餐饮点单系统设计草案

日期：2026-10-26  
项目：HotGo / GoFrame 后端  
范围：业务与后端设计，不包含本次代码、数据库或部署变更。

## 1. 已确认需求与建议默认值

### 已确认需求

- 同一品牌经营多家直营门店。
- 堂食先消费，期间支持多次加菜，最后统一结账。
- 支持顾客自助开台和员工代开台。
- 门店可配置顾客提交后是否需要员工确认。
- 顾客扫码浏览菜单不占用桌台；首次提交有效点单才发起开台。
- 同桌顾客可以加入本次用餐并继续点单；桌台二维码本身不作为加入现有账单的授权凭证。
- 结账后由员工清台，完成后供下一批顾客使用。

### 本草案采用的建议默认值

以下是便于形成完整方案的建议，不代表用户已经逐项选择；实施前可调整。

| 项目 | 建议默认值 |
| --- | --- |
| 后端组织方式 | 新增独立 restaurant 插件，沿用当前 HotGo 分层 |
| 数据设施 | MySQL 持久化；Redis 用于辅助缓存，接入项目缓存封装 |
| 顾客点单载体 | API 不依赖具体载体，首个入口建议扫码 H5，小程序可复用业务接口 |
| 收款主体 | 同品牌统一收款，交易始终保留门店归属；预留门店收款账户绑定 |
| 结账操作 | 员工发起并确认应收金额，顾客在线付款或员工登记现金收款 |
| 支付渠道 | 首先接入一个实际使用的线上渠道及现金，再按需求增加渠道 |
| 菜单价格 | 总部提供默认价格，门店可选择跟随总部或独立定价 |
| 库存 | 管理菜品规格的可售份数及售罄，不包含原材料配方扣减 |
| 账单合并范围 | 一桌一次用餐一张账单，第一期不做并桌、拆账、挂账和混合支付 |
| 员工确认范围 | 开启时，顾客首次点菜和后续加菜均需确认；授权员工代点直接确认 |
| 同桌加入方式 | 当前用餐短期加入码，或员工确认加入；加入凭证随用餐结束失效 |
| 报表营业日 | 默认按门店当地自然日，保留时间和门店信息，后续可扩展跨日营业日 |

## 2. 业务边界与使用端

总部管理门店、员工权限、菜品基础资料、价格策略及跨店经营数据。门店管理本店桌台、用餐账单、点单、退菜、厨房任务、结账与交班。

| 使用端 | 功能 |
| --- | --- |
| 总部后台 | 门店、菜单、授权、收款配置、跨店报表 |
| 门店工作台 | 开台、代客点单、审批、退菜、结账、退款、清台、交班 |
| 顾客端 | 浏览菜单、发起用餐、加入用餐、点单加菜、申请退菜、查看账单、付款 |
| 厨房看板 | 查看已确认菜品、制作、部分出餐、出餐完成、异常和催菜 |

第一期不包含外卖配送、外卖平台对接、团购核销、会员储值、复杂套餐、原材料采购、换桌并桌和按人拆账。

## 3. 后端架构与现有能力复用

采用模块化单体，不拆分微服务。餐饮业务集中在插件中，内部划分门店、菜单、用餐、点单、结账、厨房和报表职责。

- 沿用 API → Controller → Service → Logic → DAO 分层。
- 按现有插件规则注册路由，管理端与顾客端分别鉴权。
- 复用后台账号、角色菜单、文件上传、字典、操作日志和任务基础设施。
- 顾客身份与管理员身份分开，不将后台管理员当作餐饮顾客。
- DAO、entity、do 按项目规范从表结构生成；业务逻辑不放入 Controller。
- 菜单缓存通过项目缓存封装访问，键包含门店与版本；价格和库存提交时重新校验。
- 数据库事务负责订单和份数一致性，不依赖缓存锁保证资金或库存正确。

当前 admin_order 主要是后台充值模型，不复用为餐饮账单。现有支付创建读取统一配置，适配餐饮时需要注册独立业务处理，并核查金额单位、通知验证、错误传播及重试机制。已有支付代码不能直接视为已经满足本设计。

## 4. 核心业务模型

### 4.1 桌台、用餐账单与点单批次

```text
门店
└─ 桌台（长期存在）
   └─ 当前用餐账单（每次接待新建）
      ├─ 首次点单批次 → 多条菜品明细
      ├─ 加菜批次 1 → 多条菜品明细
      ├─ 加菜批次 2 → 多条菜品明细
      └─ 结账记录 → 支付尝试 → 退款记录
```

第一期由用餐账单同时承载本次用餐会话及消费归集，不额外创建与账单一对一、状态重复的会话表。参与人表保存本次用餐成员及其授权。

每次提交创建一个不可被后续加菜覆盖的批次。同一菜品出现在不同批次时，保留各自价格快照和制作记录；展示可汇总，持久化不合并历史批次。

### 4.2 总部菜品与门店菜单

总部维护菜品、分类、规格、口味和加料。门店维护是否售卖、售价、可售份数、售罄、售卖时段及厨房档口。

价格明确区分跟随总部与门店独立定价。点单保存菜名、规格、加料、单价等快照；已提交批次不因菜单更新自动改价。审批时若价格或库存失效，拒绝该批次并返回原因，不静默替换顾客已确认的价格。

### 4.3 数据隔离

- 门店业务记录关联 store_id，跨表关联校验相同门店和账单归属。
- 员工与门店为多对多关系，角色权限与可访问门店范围分别控制。
- 总部账号仅在其被授予跨店权限时访问多店数据。
- 列表、详情、写入、导出、任务、缓存及实时消息均应用相同范围校验。
- 顾客只访问其被授权加入的有效账单，不能仅凭账单 ID、桌号或 store_id 获取权限。
- 门店不是租户。第一期按单品牌多门店设计，不将现有 tenant_id 直接用作 store_id。

## 5. 开台和入桌流程

### 顾客自助开台

1. 扫码解析有效门店和桌台标识，检查营业状态及桌台是否可用。
2. 浏览菜单不创建账单、不占桌。
3. 首次提交包含人数、菜品、短期点单凭证和幂等标识。
4. 在事务内锁定桌台并检查当前账单，创建唯一活动账单及首个批次。
5. 无需确认的门店直接确认批次、扣减份数并生成厨房事件。
6. 需要确认的门店将账单置为待确认，不扣减份数、不下发厨房；员工接受时再次核价和校验库存。
7. 待确认占用建议 5 分钟自动过期，员工可以主动拒绝并释放桌台；过期后迟到的审批必须失败。门店可调整超时值。

同桌多人同时首次提交时，只有一个请求可创建活动账单；其他顾客进入加入流程，不能仅因同桌号就自动获得账单权限。事务锁和数据库约束保证唯一性。

### 员工代开台

员工选择其权限范围内的空闲桌台，填写人数，创建用餐中的空账单，随后可代客点菜或帮助顾客加入。误开台可由授权员工结束，但必须没有有效消费及未决支付，且记录原因。

### 加入本次用餐

首位顾客或员工获得本次用餐的短期加入码，同桌人员扫码后再验证加入码，也可由员工确认。加入码应限次、限时、限制尝试频率；授权通过后签发绑定顾客、门店和账单的会话凭证。

静态桌台二维码无法证明顾客仍在店内。第一期通过短期扫码凭证、接口限流、待确认超时和可选员工确认降低远程占桌风险；需要更强控制的门店启用员工确认。结清时撤销点单权限，清台后旧入桌凭证不得加入下一张账单。

## 6. 状态与业务约束

| 对象 | 状态 |
| --- | --- |
| 桌台 | 空闲、待确认、用餐中、待清台、停用 |
| 用餐账单 | 待确认、用餐中、结账中、已结清、已取消 |
| 点单批次 | 待确认、已确认、已拒绝、已取消 |
| 支付尝试 | 待支付、处理中、成功、已关闭、失败 |
| 退款 | 申请中、处理中、成功、失败 |

厨房按明细维护待制作、制作中、已出餐及取消数量；支持一条明细部分制作、部分出餐和部分退菜。各有效数量不能超过已确认数量；退菜校验制作进度。

顾客追加批次是否需审批按门店配置决定。已确认批次不允许通过普通编辑接口删除或修改数量，调整必须走退菜或新增批次。

结账前必须处理所有待确认批次、退菜申请及影响金额的审批。存在未出餐菜品时提示收银员确认，允许顾客提前结账；账单结清不会取消有效厨房任务。清台前需要完成或按授权流程处理未结束的厨房任务。

## 7. 退菜、库存、优惠与金额

- 金额使用整数分；外部支付接口的单位转换在边界统一处理。
- 待确认批次不扣库存；确认时事务校验并扣减可售份数，失败则整个批次不确认。
- 无限份数与有限份数明确区分，不能用含义不清的负库存表示。
- 未制作退菜经确认后减少应收，符合恢复规则时返还份数。
- 已制作或已出餐退菜需授权，记录损耗，不自动返还可售份数。
- 未付款退菜不产生退款；结清后退菜通过关联原明细的售后与退款处理，不改写原始结账快照。
- 赠送菜品保留出餐和库存记录，金额通过优惠调整表达。
- 折扣、赠送、抹零和改价记录操作人、原因、调整前后金额及权限校验结果。
- 整单优惠按有效菜品金额分摊，整数分余数按固定顺序补齐，分摊总额必须等于整单优惠额。

结账应收 = 菜品原价金额 − 已批准退菜金额 − 优惠金额 − 抹零金额 + 明确配置并展示的费用。

第一期默认不收餐位费和服务费；若启用，应在下单前展示并保存账单快照。退款上限以已实收减去成功退款及处理中退款占用额为准，防止并发超额退款。

## 8. 统一结账与支付一致性

1. 收银员请求试算，服务端返回账单版本、有效明细和金额。
2. 发起结账时在事务内校验版本及未决审批，将账单切换为结账中并保存结账快照。
3. 结账中禁止加菜、退菜、改价和优惠调整。并发加菜必须先于锁定完成并纳入试算，或明确失败。
4. 线上支付单保存结账记录、门店、渠道和收款账户快照；现金收款保存收银员及班次。
5. 通知验签并核验交易号、金额、币种、收款账户及业务关联；客户端支付成功页面不能直接结清账单。
6. 确认实收后，幂等更新支付及账单、写入事件，桌台进入待清台。
7. 定时查询未知或长时间处理中交易，与渠道账单对账，修复支付成功但业务状态未更新的情况。

每个结账记录同一时刻最多允许一个可成功收款的支付尝试。更换渠道或改为现金前，先关闭旧线上交易并查证最终状态；状态未知时保持冻结，不能通过本地标记失败直接再收一笔。

撤销结账仅限未实收且不存在未知支付结果的情况。确认所有旧支付尝试已关闭后，旧结账记录作废、账单版本递增，恢复用餐中，重新核价后方可再次结账。异常迟到的成功支付按原支付尝试归属处理并进入人工核对或退款，不能误结清新版本账单。

## 9. 厨房任务和可靠通知

批次确认与待发送事件在同一数据库事务提交。事务完成后由后台任务投递厨房通知，重试使用同一事件标识，消费者通过唯一键去重。

实时推送只用于提醒，厨房端重连后按持久化任务及游标补拉，不能只依赖 WebSocket。批次和明细是实际制作依据。

催菜只增加催菜事件，不重复创建制作任务。打印机作为后续可接入设备，第一期至少完成厨房看板；接打印时需记录发送、设备确认、失败和补打。无法确认是否已经打印的任务提示人工处理，避免无限自动重打造成重复制作。

## 10. 逻辑表与约束建议

以下为逻辑名，最终表前缀按插件和项目生成规范确定。

| 数据组 | 逻辑表 | 关键内容 |
| --- | --- | --- |
| 门店人员 | store、staff_store、store_business_rule | 门店、员工可访问范围、营业与点单规则 |
| 桌台 | table_area、dining_table | 区域、桌号、状态、current_bill_id |
| 菜单 | category、dish、dish_sku、dish_option | 总部菜品、规格、口味加料 |
| 门店售卖 | store_dish、store_sku | 上架、价格策略、可售份数、售卖时段 |
| 顾客 | customer、customer_identity | 独立顾客与登录身份 |
| 用餐 | dining_bill、bill_participant、bill_join_token | 本次用餐、成员授权、短期加入凭证 |
| 点单 | order_batch、order_item、order_item_option | 每次提交、菜品快照、选项快照 |
| 调整 | return_request、bill_adjustment、operation_log | 退菜申请、优惠调整、审计 |
| 结账 | settlement、payment_attempt、refund、refund_item | 结账快照、收款尝试、退款及菜品关联 |
| 收款配置 | store_payment_binding | 门店与收款账户配置引用，不存明文密钥 |
| 库存出餐 | stock_movement、kitchen_task、outbox_event | 份数流水、制作任务、可靠事件 |
| 收银 | cashier_shift、cash_receipt | 班次、现金确认、交班统计 |

关键约束：

- 门店内桌号唯一；桌台 current_bill_id 在锁定桌台的事务中维护。
- 门店与规格售卖记录唯一；库存变动按业务动作唯一，重试不得二次扣减或返还。
- 下单幂等键绑定提交者、账单或开台请求及请求内容摘要，同键不同内容拒绝。
- 账单版本在影响应收或结账状态的修改时递增。
- 结账记录保存明细与优惠分摊快照，支付渠道交易号按渠道及收款账户范围唯一。
- 退款业务号、厨房任务业务键及事件标识唯一。
- 交易记录不提供通用删除接口，通过取消、退菜、退款及审计纠错。
- 常用列表按 store_id 与状态、创建时间建立组合索引，实际执行计划在实现阶段验证。

支付与退款逻辑表最终可通过扩展现有支付日志实现，但必须保持上述账单关联、账户快照和幂等约束，避免重复建立两个相互冲突的支付事实来源。

## 11. 接口边界

| 接口组 | 业务操作 |
| --- | --- |
| 总部管理 | 门店、员工授权、菜品、门店菜单、收款绑定、跨店报表 |
| 顾客入口 | 解析桌码、菜单浏览、首次点单、加入用餐、账单查询、加菜、退菜申请、获取支付参数 |
| 门店操作 | 员工开台、代点、点单确认或拒绝、退菜审批、账单调整、结账试算、发起或撤销结账、现金确认、退款、清台 |
| 厨房 | 待制作列表、开始制作、部分出餐、完成出餐、异常处理 |
| 内部任务 | 支付通知、退款通知、未知交易查询、待确认超时、事件重试、对账 |

写接口使用专用业务动作，不用一个通用编辑接口直接修改订单状态或支付金额。接口输入输出、错误码和数据库字段在设计评审后进一步细化。

## 12. 报表与审计口径

- 消费报表以结账快照展示有效销售额、优惠、赠送和退菜，关联原账单。
- 收款报表按实际支付成功时间统计实收，按退款成功时间统计退款；净收款为同期实收减同期退款。
- 菜品销量按已确认有效数量和退菜记录计算，明确区分经营销量与厨房出餐量。
- 门店流水按原交易门店归属，不因员工调店、菜品下架或门店改名改变历史归属。
- 跨日未结账单独列示，不当作当日实收。
- 现金按收银员和班次交班；线上渠道账单与本地支付及退款逐笔对账。
- 退款、改价、赠送、抹零、作废和补打全部留痕；日志不记录密钥及完整敏感支付数据。

## 13. 分阶段交付与验收

### 阶段一：门店和菜单

完成门店、员工范围、桌台、总部菜品、规格和门店价格。验收跨店越权被拒绝，门店价格独立生效，总部调价不会覆盖独立定价。

### 阶段二：开台、点单与厨房

完成自助与员工开台、加入用餐、多次加菜、员工确认、可售份数、退菜和厨房看板。验收同桌并发首次点单只产生一张活动账单；最后一份不超卖；拒绝或超时正确释放待确认占用；历史加入凭证无法访问下一次用餐。

### 阶段三：结账和资金

完成版本化试算、结账冻结、一个线上渠道及现金、退款、清台和交班。验收加菜与结账竞态、重复支付通知、撤销与迟到通知、渠道未知状态、并发退款，以及优惠分摊后的部分退款金额正确。

### 阶段四：经营与稳定性

完成门店及总部报表、渠道对账、事件补偿和运行告警。验收厨房断线恢复不漏单、重复事件不重复制作、支付已成功但业务更新失败可恢复、跨日收退款统计口径明确。

本文件是完整业务草案，不是已经完成的实现说明。后续依次细化表结构与约束、接口契约、开发任务及验证用例，再进入编码。
